# Working on Langmake

Langmake is an independent C++20 runtime with Luau game behavior and JSON projects. External agents own conversation and inference; do not add an engine-owned model connection or provider dependency.

The optional `studio/` module may host coding agents, project management and chats. Keep its provider SDKs, credentials, conversation state and desktop dependencies out of the runtime and exported games. External Codex, Claude and other directory/CLI agents remain fully supported; Studio is never a prerequisite. Maintain runtime-only and Studio distributions. Android build/deployment tools under `scripts/android/` must also work independently of Studio.

Discussing an idea is not permission to implement it. Act when the user clearly requests implementation. Keep task files, dependency downloads, build artifacts and caches inside this workspace unless the user permits another location. Do not install global tools.

Read `README.md` for current status, `docs/08-agent-api.md` for the working command contract and `docs/13-runtime-guide.md` for gameplay/asset authoring. `build/langmake.exe capabilities`, `schema`, `script-api` and `asset schema --type TYPE` describe the implemented subset. The broader plan in `docs/` includes future features; do not advertise those as supported.

Start game work with `langmake context --project GAME` and `docs/26-game-workflow.md`. Targets are explicitly configured per game/machine in ignored `.langmake/targets.local.json`; never inherit another game's SSH configuration, Mac path, signing team or device. Use named scenarios, bounded receipts, resumable operations and generated `HANDOFF.json` instead of task-local deployment glue. Keep portable application identity/icons/profiles separate from local machine configuration and credentials. The `workflow-2d` starter demonstrates these contracts; humans still decide the game and playtest it.

For any Android game creation or port request, read `docs/21-android-agent-guide.md` before authoring. It gives the required documentation order, source/portable/Studio paths, exact build and device workflow, native request/receipt semantics, and human handoff criteria. Do not infer Android commands from desktop flags. Keep this guide and its discovery links current with engine changes.

For iOS/iPadOS game or port work, read `docs/23-ios-agent-guide.md` and `docs/24-ios-qualification.md` first. Use `scripts/ios/ios.py` independently of Studio. Apple native builds require an authorized Mac workspace with Xcode, and physical deployment requires signing and an explicit device. Select phone/tablet presentation profiles explicitly; a universal app or iPhone result does not qualify iPad input/layout. Never infer iOS qualification from Windows tests, generated projects or library support. Keep the iOS guide, tools, discovery and prompt examples aligned.

For help structuring a human brief or agent task, read `prompts/README.md`. These optional examples cover new games, feedback, defects, assets and planning; they are inspiration, not authorization to implement or evidence of built games. The human's actual brief takes precedence.

When changing engine commands, behavior, templates, asset formats, saves, supported platforms or the human/agent workflow, review affected files in `prompts/` in the same change and update them if needed. Follow the maintenance checklist in `prompts/README.md`, record the reviewed version/date, and keep source/portable discovery links and packaged copies aligned. Regenerate distribution copies from canonical sources; do not edit only `dist/`. Keep historical runtime qualification separate from documentation-only verification.

The human is the decision-making game developer and primary gameplay playtester. AI agents are worker developers who implement the human's ideas, handle technical verification and prepare playable iterations. Read the human-directed workflow at the start of `docs/08-agent-api.md` before game work. Complete the authorized iteration autonomously; do not seek permission for every implementation detail. At meaningful playable milestones, hand the game to the human with launch instructions, controls, changes, known issues and focused feedback prompts. Human feedback directs the next creative iteration.

Use native validation, simulation, state inspection and captures for agent verification. Do not default to computer-use gameplay or autonomous full playthroughs as a substitute for the human playing. Supplementary agent playtests are appropriate when requested or for a focused bug investigation; prefer native controls, using computer use only when requested or when the input/UI behavior cannot be checked through them. Report technical checks separately from human feedback; never infer gameplay acceptance from a passing test. While the human is playing, avoid source edits, reloads, resets, pauses or injected input that would disrupt their session unless requested. Continue independent authorized work where possible; when a creative decision needs feedback, mark it awaiting human playtesting rather than inventing approval.

For game work, start from `langmake new`, inspect stable entity IDs, and edit JSON/Luau or use revision-checked patches. Use `validate`, offline Luau `check`, headless `simulate`, and fixed-tick `capture --steps N --input TIMELINE --ticks TICKS --output-dir DIR --no-overlay` with state sidecars. Filter live inspection to relevant entities/fields; add `--check-source` when confirming authored/running revision agreement. Reload restarts gameplay. Use `play --project PATH` for human handoff; it disables the developer overlay, shortcuts and source watch. Store persistent game progress in declared engine state and use explicit save migrations when content changes.

Build: `powershell -ExecutionPolicy Bypass -File scripts/build.ps1`.
Test native/runtime behavior: `powershell -ExecutionPolicy Bypass -File scripts/test.ps1`.
Test graphics/live changes: add `-Graphics`; this opens temporary preview windows.
Package: `powershell -ExecutionPolicy Bypass -File scripts/package.ps1`.

Do not alter pinned dependency checkouts to fix integration code. Record intentional dependency changes in CMake, the revision lock and notices. Qualify each platform and feature with actual evidence; this release is a Windows/D3D11 and Android/GLES3 alpha. Read docs/20-android-qualification.md for actual device coverage. Android games use scripts/android/android.py independently of Studio; select an explicit device serial, ABI and orientation, and preserve declared gameplay state. Use dp for phone UI dimensions and fonts; native observations expose safe-area bounds.
